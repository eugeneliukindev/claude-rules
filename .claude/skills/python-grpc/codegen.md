### The types come from mypy-protobuf, not from `--pyi_out`

**Why:** `--pyi_out` types the messages only: no service stubs, and `HasField` accepts any string.
mypy-protobuf's `--mypy_out` types `HasField` with the fields that have presence, and
`--mypy_grpc_out` types servicers and stubs — `FlightServiceStub(channel)` on a `grpc.aio` channel
is a `FlightServiceAsyncStub`. The dev group holds `mypy-protobuf`, `types-protobuf`,
`types-grpcio` and, per companion package used, `types-grpcio-health-checking` or
`types-grpcio-status`. `grpc-stubs` was archived in April 2025; mypy-protobuf 4 moved to typeshed's
`types-grpcio`.

**Example:**
```bash
# WRONG — messages typed, services untyped, and HasField("gaet") passes the checker
uv run python -m grpc_tools.protoc -I proto \
    --python_out=src --grpc_python_out=src --pyi_out=src \
    proto/airapis/flights/v1/flights.proto

# CORRECT — HasField checked against the fields with presence, servicers and stubs typed
uv run python -m grpc_tools.protoc -I proto \
    --python_out=src --grpc_python_out=src --mypy_out=src --mypy_grpc_out=src \
    proto/airapis/flights/v1/flights.proto
```

### Below Python 3.14, a module whose signatures name `RpcMethodHandler` postpones its annotations

**Why:** `types-grpcio` makes `RpcMethodHandler` generic and the runtime class is not, so a
signature that subscribes it raises `TypeError` at import unless the module has
`from __future__ import annotations`. The stubs also lag behind the runtime: the health stubs lack
`grpc_health.v1.health.aio` and every method of `HealthStub`, so that import or call carries
`# type: ignore[attr-defined]` and its reason.

**Example:**
```python
# WRONG — "type 'RpcMethodHandler' is not subscriptable" when the module is imported on 3.13
import grpc


class RequestIdInterceptor(grpc.aio.ServerInterceptor):
    async def intercept_service[RequestT, ResponseT](
        self,
        continuation: Callable[
            [grpc.HandlerCallDetails], Awaitable[grpc.RpcMethodHandler[RequestT, ResponseT] | None]
        ],
        handler_call_details: grpc.HandlerCallDetails,
    ) -> grpc.RpcMethodHandler[RequestT, ResponseT] | None:
        _request_id.set(_request_id_from(handler_call_details.invocation_metadata))
        return await continuation(handler_call_details)


# CORRECT — the annotations stay strings at runtime, and the stubs' generics type-check
from __future__ import annotations

import grpc


class RequestIdInterceptor(grpc.aio.ServerInterceptor):
    async def intercept_service[RequestT, ResponseT](
        self,
        continuation: Callable[
            [grpc.HandlerCallDetails], Awaitable[grpc.RpcMethodHandler[RequestT, ResponseT] | None]
        ],
        handler_call_details: grpc.HandlerCallDetails,
    ) -> grpc.RpcMethodHandler[RequestT, ResponseT] | None:
        _request_id.set(_request_id_from(handler_call_details.invocation_metadata))
        return await continuation(handler_call_details)
```

### The generated tree's top-level name is one no hand-written package has

**Why:** the directory below `-I` is the import path: generated modules import each other by it
(`from airapis.flights.v1 import flights_pb2`), and protoc writes no `__init__.py`. A generated
`airline/flights/v1` beside the application package `airline` is shadowed by it, and the import
fails with `ModuleNotFoundError`.

**Example:**
```text
# WRONG — the generated airline.flights.v1 is shadowed by the application's airline package
proto/airline/flights/v1/flights.proto
src/airline/__init__.py
src/airline/flights/v1/flights_pb2.py

# CORRECT — a top-level name of its own for the API, beside the application's
proto/airapis/flights/v1/flights.proto
src/airline/__init__.py
src/airapis/flights/v1/flights_pb2.py
```

### `grpcio` and `protobuf` are declared at least at the generator's versions

**Why:** generated code pins its runtime floor: `_pb2_grpc.py` raises `RuntimeError` on import when
the installed `grpcio` is older than the `grpcio-tools` that generated it, and `_pb2.py` refuses a
`protobuf` older than its generator. The generator is bumped only with them.

### Generated files are never edited, and CI proves they match the schema

**Why:** whether the files are checked in or generated by the build is decided once. Checked in, a
`.proto` changed without regenerating — or a generated file edited by hand — ships code that does
not match the schema; CI regenerates and fails on any difference. Either way the linters skip them.
