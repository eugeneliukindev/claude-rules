# claude-rules

Правила и скилы для Claude Code: как писать Python. Всё лежит в `.claude/` и
устанавливается в `~/.claude/`, откуда Claude Code читает их в каждом проекте.

## Что где

| Путь | Когда загружается |
|---|---|
| `.claude/rules/python/*.md` | при первом чтении `.py` файла: у каждого файла `paths:` во front matter |
| `.claude/rules/python/new-files.md` | в каждой сессии — единственный файл без front matter: закрывает случай, когда проект создаётся в пустой папке и читать ещё нечего |
| `.claude/skills/python-*/` | описание попадает в список, когда прочитан или записан файл из `paths:` скила; сам скил загружается, когда работа совпала с описанием, или по `/имя` |

Карта Python-скилов — таблица в `.claude/rules/python/core.md`. Как писать и проверять правила —
скил `python-rules-authoring`.

## Установка

Правила и скилы копируются в `~/.claude` поверх старых. Синхронизация зеркальная внутри каждой
папки, так что удалённые в репозитории файлы исчезают и там; ничего вне этих папок не трогается.

```bash
rsync -a --delete --exclude __pycache__ .claude/rules/python/ ~/.claude/rules/python/
for skill in .claude/skills/*/; do
  rsync -a --delete --exclude __pycache__ "$skill" ~/.claude/skills/"$(basename "$skill")"/
done
```

Скилы, удалённые из репозитория, синхронизация не трогает — их каталоги в `~/.claude/skills/`
удаляются руками:

```bash
for skill in ~/.claude/skills/python-*/; do
  [ -d ".claude/skills/$(basename "$skill")" ] || rm -r "$skill"
done
```

Если задан `$CLAUDE_CONFIG_DIR`, подставьте его вместо `~/.claude`.

## Проверка

```bash
python .claude/skills/python-rules-authoring/scripts/check_rules.py .claude
```

Exit 0 — чисто. Скрипт проверяет бюджет: во всём, что грузится для каждого `.py`, не больше 100
правил и около 22 000 токенов, а для тестового файла вместе с `testing.md` — 120 правил и 28 000
токенов. Скил — один `SKILL.md`, не больше 500 строк и 6 000 токенов, без других `.md` рядом и ссылок на
них; что не влезает, вырезается, а не выносится (`docs/rules-history.md`). А ещё — что каждый `python`-блок парсится, что упомянутые скилы и
файлы существуют, что `core.md` называет каждый скил и что у каждого `SKILL.md` есть `name`,
`description` и `paths`; что скил называет соседа только во вступлении; что функция, класс или
константа из примеров одного скила не встречается в примерах другого скила и в правилах; что
настройку (таймаут, лимит, TTL) функция получает keyword-параметром со значением по умолчанию. Что он не проверяет и что делается руками: каждый `CORRECT`-пример проходит
`mypy --strict` и запускается против библиотеки той версии, которую называет скил.

## Evals

Состояние до рефакторинга скилов — коммит `10cdec7`; с ним сравниваются новые версии.

Поведенческие кейсы лежат в `evals/python/*.json`: реалистичная задача, которая не называет правило,
файлы для старта и проверки — какие скилы вызваны, какие файлы прочитаны, какие
регулярки есть или отсутствуют в написанном коде. `evals/run.py` гоняет каждый кейс в `claude -p` в
пустом рабочем каталоге и пустом `CLAUDE_CONFIG_DIR`: рука `with` копирует туда `rules/python` и
скилы `python-*`, рука `without` — ничего, так что чужие правила, хуки и плагины не мешают ни той,
ни другой. Логин передаётся токеном текущей сессии в окружении; результаты пишутся в
`evals/results/`, который не коммитится.

```bash
python evals/run.py --check                                  # только проверить файлы кейсов
python evals/run.py --arm both --model sonnet                # все кейсы, обе руки
python evals/run.py --only python-sync --runs 3 --arm both   # один файл, три прогона на руку
```

Проверка, которая проходит и без правил, проверяет то, что модель делает сама, — её правило
кандидат на удаление (раздел Evaluation в `python-rules-authoring`).
